Three findings reported and corrected during review
--------------------------------------------------
1. Normal transfer shutdown could be mislabeled as watchdog failure.
   The controller writes completion and stops its service in finally. Watchdog and
   supervisor can therefore exit before the controller itself returns. The earlier
   coordinator checked watchdog exit before its supervisor grace path and could
   report an ordinary completed run as failed. The current coordinate_launch.py
   running loop treats either exit alike, waits up to 45 seconds for controller,
   then checks its return code and all_queued_jobs_complete on the next loop.
   Final service.stop() checks exact process and GPU absence before successful cleanup.

2. SIGTERM immediately after admission replacement could skip restoring admission.
   The previous code set admission_written=True after os.replace. A signal between
   these operations could enter finally with a false flag despite an installed peer.
   Current code records candidate installed_admission before replacement and finally
   compares actual file bytes against installed and old bytes. It restores only its
   own exact installed content, only after transfer process and compute absence;
   third-party changes are preserved and reported rather than overwritten.

3. Main service HTTP shutdown could falsely invalidate otherwise normal completion.
   The first lifecycle fix still called exact_primary(), including GET /queue, from
   every guard. During normal shutdown HTTP may close while the exact PID remains
   alive. The current guard uses observe_primary() without HTTP; initial authorization
   still checks the live main service and archives its queue snapshot. This separates
   admission-time evidence from subsequent normal shutdown ordering.

Additional normal-completion race explicitly checked
----------------------------------------------------
primary_lifecycle.py re-reads the entire original registry every iteration. If the
original PID has become absent/zombie and all_queued_jobs_complete is already durable,
but cleanup.json still describes an older instance (for example 20176 rather than the
current original instance 49019), CleanupPending is raised, not an immediate abnormal
exit. observe_primary waits at most 45 seconds for the exact cleanup record. Reaping,
missing cleanup, and incomplete cleanup share that bounded grace. A new registry or
reused PID fails immediately even during grace. Timeout fails closed.

Verified mechanisms and isolation
---------------------------------
A. Pre-CUDA barrier:
   compatibility_bootstrap.py production main invokes wait_for_release before install()
   (the first torch import), install_video_compat (PyAV), backend adapters, or Comfy.
   Its top-level imports and startup_barrier.py are stdlib-only. Normal service.command()
   cannot select --check; --check is a separate explicit CPU diagnostic route.
   Gate lifetime <=180 seconds, nonce-bound ready/release files, exact CUDA UUID,
   pinned deployment roots, and matching service registry/ready identities are checked.
   The coordinator records the transfer PID and installs primary admission while the
   service is still blocked, starts watchdog, and only then releases the barrier.

B. Exact peer admission:
   External identity is UID + /proc start_ticks + SHA256 of raw cmdline bytes; local
   service ownership additionally uses the original full command and GPU/port.
   Release validates exact peer identities and SHA256 of both admission files, with
   exactly one matching peer row each. Existing primary peers are retained. Other
   users' compute is not classified or signaled. Selected transfer GPU must be empty.
   Target GPU0 UUID and port8461 differ from main GPU2 UUID and port8460.

C. Failure cleanup ownership:
   Coordinator signals only recorded local children with unchanged identity and RUN
   in their command; transfer service.stop additionally verifies its GPU, port, command
   and identity before SIGTERM/SIGKILL. There is no primary signal or primary restart.
   Controller is stopped before transfer service cleanup, preventing new submissions.
   Exact process/compute absence is required before removing the transfer peer entry.
   Watchdog verifies coordinator identity and the shared primary lifecycle contract;
   on failure it stops only the task-owned transfer service.

D. Shared files:
   launch_remote.prepare writes transfer input/output/user/temp/process/log/config
   paths, symlinks to task-local extensions and shared KJ nodes, and reads model/core
   provenance. It does not install dependencies or write model/core source files.
   PYTHONDONTWRITEBYTECODE=1 is passed to service and helper children. Model reuse is
   verified by original recorded hash agreement plus current size/mtime; weights are
   deliberately not fully rehashed. Core files are actually SHA256-checked.
   This is read-only by code convention, not an OS-enforced read-only mount/sandbox.

Non-blocking operational limits / conditions
-------------------------------------------
* compare_replace is compare-before-write plus atomic rename, not a kernel CAS.
  Correctness against other writers depends on honoring admission.parallel_transfer.lock.
  Root must not bypass that lock to rewrite main admission during transfer.
* A SIGKILLed coordinator cannot restore admission. The watchdog can release its
  exact service; the stale exact peer permission then requires root audit/removal.
* The pre-CUDA gate/release still requires the original primary to be live. If the
  primary completes during that short handshake, launch aborts safely before CUDA;
  the natural-completion continuation branch applies to the released runtime.
* The initial primary must be live for exact_primary() and its queue snapshot.
  This bundle is not a standalone launcher for a primary already completed before start.
* If startup fails before both service registry and token-ready evidence are available,
  cleanup intentionally avoids assuming an old registry belongs to this launch. An
  untracked pre-CUDA child can remain until the <=180-second barrier timeout; no release
  means it cannot reach the production torch import. This is bounded cleanup latency,
  not proof of immediate process removal in every pre-ready failure case.
* No automatic new-primary authorization exists. Root's stated policy is not to restart
  main service or launch a new main-GPU decoder before transfer finishes.
* Startup headroom checks do not reserve the host/GPU from unrelated users; subsequent
  host jobs or memory pressure may still cause operational failure. No other user's
  process may be stopped to recover capacity.
