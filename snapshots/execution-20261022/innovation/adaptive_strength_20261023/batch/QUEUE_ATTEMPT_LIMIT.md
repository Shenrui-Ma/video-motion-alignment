# 每条任务的尝试次数上限

候选文件：`durable_comfy_queue.after.py`。原队列文件和所有远端进程均未修改。

`Runner.run_job` 接受任务 JSON 的可选 `max_attempts`。值必须是正整数且不超过启动参数 `--max-attempts`；布尔值、浮点数、字符串、空值和越界值按无效任务记录，然后继续下一条任务。没有该字段时仍使用全局上限。

新八条实验设置 `"max_attempts": 1`：已提交的科学方法运行失败或成片校验失败后结束该条，不按相同配置再次提交。服务在提交前尚未就绪时，原有等待与管理服务恢复逻辑保持不变，不消耗提交次数。

已保存的 `prompt_id` 继续轮询，即使历史尝试数已经达到或超过新上限。`submitting` / `submission_unknown` 继续按原任务 ID 和 attempt token 查询队列及历史；找到就接管已有任务，未找到则保留未知状态，不重复提交。恢复到已失败的提交后，已耗尽的任务进入 `failed`。

补丁仅增加四行配置解析和验证，并将原 while 条件中的全局上限替换为该任务的有效上限；所有恢复条件保留。原状态格式、图哈希、锁、任务归属和提交事务顺序不变。

## 验证

本地运行 `python3 verify_queue_attempt_limit.py`，临时目录中使用候选队列和 localhost HTTP 模拟 ComfyUI。原有 14 项回归与新增 9 项测试全部通过，共 **23/23**，13.383 秒。覆盖默认全局次数、任务上限、非法值、继续下一条、断连恢复、重启恢复、未知提交不重复、已知 prompt 超过新上限仍继续，以及耗尽后重启不重投。

证据：`queue_attempt_limit_test_result.json`，含原文件、候选文件、原测试集的 SHA256。差异文件：`durable_comfy_queue.max_attempts.patch`。

部署由主线程完成：先核对当前进程身份与任务状态，部署候选文件，并仅给新批任务增加该字段。已运行的 Python 进程不会因修改磁盘文件自动换用新逻辑。
